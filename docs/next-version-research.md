# 第二轮研究与下一版实施规格

研究日期：2026-10-30。状态：研究及设计建议，下面描述的下一版功能均未实现。当前可运行版本仍是 v0.1.0。

## 1. 判断与证据边界

目标是让带练者在每个检查点判断“等、继续、共同排障或个别协助”，并让被留下的人仍能恢复跟上。项目小指部署和参与成本低，不应意味着只有统计按钮。

已知事实：当前项目具备真实后端、SQLite、SSE、按步骤隔离和卡点赞同；本机 10 项测试通过。上一轮审计另复现同 IP 心跳耗尽写限额、完成后重复赞同把状态改回受阻两个问题。未运行真实课堂、持续负载、完整部署或弱网自动化试验。

研究主要来自官方介绍、公开 README、GitHub API。未购买商业服务；dekita 的浏览器加载超时，功能只能根据官方索引页面确认，未完成交互实测。不用“未在介绍中出现”推断竞争者没有某功能。星数、最近 push 为当日快照，push 也不等于有实质维护。以下是产品假设，不是用户验证结果。

## 3. 推荐定位与首选场景

定位：一个免注册、可自部署的操作带练协调工具，围绕检查点协调全班推进和个别恢复。

首选验证场景：10–30 人、30–90 分钟、4–10 个检查点的软件安装或编程环境配置；一名讲解者，可选一名助教。任务完成标准较容易描述，环境差异又会造成共同卡点。

暂不面向：纯讲授课程的理解程度打分、长期班级成绩管理、大规模考试、自动设备监控或任意流程管理。状态是主动报告，点击完成不能证明安装成功或已经理解。

选择理由是产品推断：这一范围更容易观察“少问、早发现、处理后跟上”，并能保留轻量边界。需要通过试用确认，不能预设有付费意愿。

## 4. 核心体验：一场课怎样完成

1. 准备：手动列出检查点，每步包含标题、完成标准、可选帮助链接、可选常见原因；临场仍可直接新增步骤。保存或复制为本地模板。
2. 入场：扫码或房间码加入，昵称或自动分配别名。首屏显示当前任务和三个反馈按钮。讲解者可选填预计人数，识别尚未加入的人数差额，但不能知道未加入者是谁。
3. 操作：三个按钮单击提交，显示待发送/已确认/失败；“卡住了”立即生效，再可选点原因或写补充。不能以填写原因作为受阻反馈的前置条件。
4. 排障：问题归在对应步骤；讲解者将同类卡点手动合并，发布短说明或安全的帮助链接。相关参与者收到页内提示。
5. 恢复：参与者选择“已解决，继续操作”或“仍然卡住”。只有参与者明确完成当前操作，才进入完成。讲解者回应不会替他们完成。
6. 推进：主持看到当前完成、未反馈、受阻与前序未解决。推进需要确认保留的尾项，不能默默清空。无助教时可选择再等或先继续并保留跟进；有助教时可指派尾项。
7. 收尾：生成本次检查点复盘、问题及处理办法，导出 CSV/JSON；能复制步骤和处理经验开启新场次，但不复制昵称、状态或旧求助记录。

建议默认不启用声音、浏览器通知或自动推进。手机锁屏恢复后，先重新同步服务端状态，再允许提交，不能把陈旧操作静默套到新步骤。

## 5. 三类视图，控制规模

- 参与页：当前检查点、完成标准、三个按钮；我的未解决问题和发给我的处理办法。状态按钮在手机首屏内。全班统计可折叠，不应占据主要操作空间。
- 主持控制台：当前检查点的概况、最需要处理的共同问题、前序尾项、人员筛选、下一步及结束操作。二维码放在邀请抽屉，不永久占据大块空间。
- 投屏页：只有当前任务、汇总和经主持公开的帮助信息，不含昵称、自由文本卡点、管理操作或管理凭证。专用只读凭证，不能通过隐藏 DOM 充当权限隔离。

助教先作为可撤销的房间协助角色：可认领/回应问题，不能删除房间、修改主持权限或偷偷替学生完成。没有助教也必须能完整使用，不使其成为流程依赖。

## 6. 最关键的统计与状态规则

### 6.1 不让一个数代表三件事

分别显示：预计人数（可选）、本场有效加入人数、当前步骤参与范围、反馈人数。完成比例用当前步骤参与范围作分母；离线仍是连接属性，不自动当作离开。正式离开/移除记录时间，必须可解释分母变化。

发布下一步时冻结上一检查点的推进时快照（人数、状态、耗时），用于复盘。前序未解决问题则独立继续流转。迟到者不改变已经冻结的历史；是否需要补做前序步骤由主持说明，不强制编造完成记录。

### 6.2 当前步骤与个人未解决事项并存

全班当前步骤唯一。新步骤的自报状态从未反馈开始，但参与者页必须同时提示其前序未解决事项；首次反馈新步骤时可明确“已能继续”或“仍受前序阻碍”。不能把前序问题自动记成新步骤的新问题，也不能在统计里把前序受阻人数再加进当前步骤人数导致重复计数。

允许在下一步开启后确认旧问题恢复，但不回写冻结的推进时统计。复盘分别展示“推进时仍受阻”和“结束前已恢复”。

### 6.3 卡点与受影响的人分别建模

问题状态建议：待处理 → 处理中 → 已发布办法 → 已关闭；收到新的“仍卡住”反馈时允许重新打开。

每个人对某问题的状态：受影响 → 已恢复/退出该问题。赞同必须幂等；当前受影响人数与累计遇到人数分开显示。解决一个问题不自动解决这个人的其他问题，也不自动完成步骤。

合并仅在同一检查点内进行，保留原始标题、成员和操作记录；同一人在两个被合并问题中只能计一次。初版使用主持手动合并和预设原因，不引入不可解释的自动语义合并。

### 6.4 身份与主持恢复

继续保留免注册。讲解者创建后可下载或复制恢复凭证，通过单独入口恢复主持控制；凭证不可进入参与分享链接、公开投屏、日志或导出。

参与者只允许持有旧凭证时恢复已有身份，不能仅凭相同昵称夺取身份。跨设备的无凭证恢复暂不实现；重复身份由主持标记移除并保留操作痕迹。

## 7. 数据与工程约束

现有 FastAPI + SQLite + SSE 可先保留，不以换框架代表产品升级。为实现闭环，需要数据库迁移、窄模块拆分和事务规则。

建议增加：步骤完成标准及开启/冻结时间；成员有效期；问题成员及恢复时间；回答记录；主持/助教/只读角色；请求幂等键、状态版本、房间修订号。保留一张最小事件表记录状态变更与解决动作，避免只有最后一次状态却试图计算恢复耗时。不采集个人屏幕、安装软件清单或自动生成学生能力评分。

- 写操作携带请求 ID、步骤 ID 和预期版本；重复请求只返回原结果，迟到请求不得覆盖较新状态。
- 前端写失败必须保留输入。操作成功与状态刷新失败分开呈现，不能只弹出网络错误诱导重复发布。
- 普通请求有明确超时。SSE 有存活检测、带抖动退避和快照恢复；重连先取权威状态。页面切换清理心跳、流 reader 和监听器。
- 每个房间维护共享修订号/快照；未变更不逐连接重建整段历史。实时流主要发送当前步骤及待办变化，历史按需获取。
- 心跳与业务写请求分开限流，已加入者按凭证计量；加入/建房保留按 IP 的粗粒度防刷。同一 NAT 下多人必须可正常反馈。
- 用户可见状态依赖房间级事务快照，避免并发发布时返回跨步骤混合数据。权限在服务端强制，不依赖界面隐藏。
- 增加数据迁移/回滚及备份恢复检查；只读投屏链接可撤销，关闭房间时停止写入。自动清理须预先明确保留期，不突然丢失复盘。

## 8. 分阶段完成条件

### v0.2：能可靠带完一次活动

范围：修复已复现缺陷；参与端首屏反馈；步骤完成标准；主持/投屏分离；问题回答和成员恢复；推进时冻结快照与前序尾项；预计/有效/反馈人数口径；主持恢复凭证；可读的结束总结及 CSV。

验收：

1. 用同一出口 IP 模拟 60 个身份，持续心跳并每步反馈，30 分钟不因正常心跳误限流；这是待执行测试目标，不是已达成性能。
2. 10、30、60 人场景记录响应延迟、SSE 收敛延迟及错误率。初步目标：30 人同网环境更新 P95 在 2 秒以内，明确硬件/网络条件；超过时先优化和降级，不虚报容量。
3. 断网后点击不显示已同步，输入不丢；恢复后新旧步骤正确隔离，无重复步骤或重复问题成员。
4. 主持发布下一步后，旧问题可恢复，冻结快照不变化，新步骤人数不会重复累计。
5. 投屏凭证无法读取昵称/原始私密文本、恢复凭证或调用管理接口；助教凭证无法越权。
6. 从空环境按 README 启动；Docker 实际构建启动；持久卷重建服务后记录仍在；备份恢复演练通过。
7. CI 实际启用运行成功，而非只有模板；若仍缺 workflow 权限，作为未完成交付项如实保留，不能在版本说明中写成已完成。

### v0.3：使第二次活动更省事

增加手动检查点编排/排序、私有模板的导入导出及复制、问题手动合并、可选助教接单及撤销、按步骤分析恢复情况。先附一个可检验的环境安装示例模板，所有帮助链接由维护者校验；不堆泛化课程库。

暂缓：AI 聚类、自动监控安装结果、PPT/录音接入、完整课程管理、聊天系统、排行榜、计费和大规模多租户。开放 API 可在稳定房间模型之后考虑，不与本轮竞争开发资源。

## 9. 真实试用：如何判定值得继续

先招募 2–3 名实际带练者了解最近一次经历，追问发生了什么、现有办法、什么时候会看面板，不询问笼统的“你觉得这个创意好吗”。再做一次 10 人场景可用性试用；通过后在至少两次活动中观察约 20–30 人规模。不能用模拟数据替代。

观察指标：加入耗时；每步 30 秒内主动反馈率；每步提醒次数；从受阻到被发现时间（需要观察员或访谈，按钮时间并不代表真实受阻开始）；从处理办法发出到自报恢复时间；讲解者查看面板的频率；参与者是否愿意继续。

提出但未验证的门槛：80% 人能在 1 分钟内加入；80% 已加入参与者能在新步骤发布 30 秒内反馈；平均每步额外提醒不超过一次；相比口头/群聊流程至少发现一个更早的共同问题；下一次活动带练者主动复用。10 人试用只能筛查可用性，不能证明普遍有效或付费意愿。对照任务难度、顺序、助教数量要记录，不宣称小样本有统计显著性。

如果组织者只有被提醒才看面板、参与者不断被催才点击，优先调整反馈时机与首屏，再试一次；仍失败则缩窄到有明确检查点和协助资源的活动，必要时停止扩写。

## 10. 不可替代性与失败边界

目前没有不可替代性证据。开源、自部署和中文界面是采用理由，不能保证用户迁移。较难积累的价值是反复试用后形成的可靠步骤模板、常见卡点与有效处理办法，以及组织者的复用习惯；这些只可来自用户同意的真实数据，不天然构成商业护城河。

红队一：没有人力处理卡点时，面板再准确也不能帮人跟上。产品只能协调、提示和分发办法，不能宣传会解决教学资源不足。

红队二：参与者不愿点按钮时，自报数据会失真。不能自动把沉默算完成，也不能靠增加催促来伪造成功。试用要同时衡量信息收益和额外负担。

红队三：即使做完整，通用工具也可能复制此流程。应验证“第一次就能用、第二次更省事”，而不是继续追逐功能独占。

本轮修改范围仅为研究文档，没有实现上述功能，也没有新部署、容量测试或真实课堂结果。
